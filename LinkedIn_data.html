I passed the Neo4j Certified Professional exam

September 2026

There are different retrieval strategies for RAG systems. One of them is vector search followed by graph traversal. The neo4j-graphrag Python package implements it as VectorCypherRetriever.

Two steps. Embed the question, run similarity search against the vector index, get back the matching nodes. In a document graph those are chunks. Then a Cypher query you write expands from them to pull in what they connect to.

For instance, say the seed node is a contract clause. The traversal returns:

  • the contract it sits in
  • the parties who signed it
  • the amendments that changed it

None of that is in the chunk.

In Neo4j, the embeddings and the graph live in the same database. Similarity picks the seed nodes, the graph expands outward from them, and what comes back is connected context instead of an isolated chunk.

Serverless LLM Inference for Privacy-Sensitive Use Cases

May 2026

Some use cases can't use hosted LLMs. The acceptable data risk isn't "low." It's zero.

I integrate hosted LLM APIs into backends when the problem domain is inherently fuzzy and reasoning genuinely helps. Lately mostly Claude, Gemini, and DeepSeek. DeepSeek in particular is remarkably cheap and a great choice for non-sensitive workloads.

But sometimes privacy is a dealbreaker. A strong privacy policy doesn't prevent breaches, subpoenas, or the gap between what a company says and what it does operationally. No hosted solution can close that gap. The trust surface is too large and too opaque.

One obvious answer is Ollama. Run the model locally, zero data leaves your infrastructure. Great for local development. But a persistent GPU rental for sporadic usage is a bad economic fit; idle cost kills it.

I wanted something that runs a capable open-weight model on real GPU hardware, with an OpenAI-compatible endpoint so nothing in my integration changes, and costs nothing when I'm not using it.

I ended up deploying vLLM on serverless GPU infrastructure via Modal, serving Qwen3. Switching from a hosted provider to this is a one-line config change. You only pay for actual inference time; idle cost is zero. Your data never reaches a model provider's systems. Modal is still a third party, but the trust surface is meaningfully smaller: they have no incentive to train on your data, the blast radius of a compromise is narrower, and their infrastructure role is compute-only rather than model development.

The main tradeoff: cold starts. The first request after a period of inactivity takes roughly 30 seconds while the model loads. For sporadic, privacy-sensitive use cases, that's a reasonable price.

The less obvious benefit: you own the weights, so fine-tuning becomes an option. That door is permanently closed with any hosted API.

Copying Array Methods in TypeScript 5.2

TypeScript 5.2 includes definitions for the methods added to ECMAScript in the Change Array by Copy proposal [https://lnkd.in/eguyxsxS] which provides additional methods on Array.prototype and TypedArray.prototype to enable changes on the array by returning a new copy of it with the change.

The Tuple.prototype introduces these functions as a way to deal with the immutable aspect of the Tuples in Record & Tuple. While Arrays are not immutable by nature, this style of programming helps when dealing with frozen arrays for instance. This notably makes it easier to write code able to deal with Arrays and Tuples interchangeably.

Astral Symbols in TypeScript and JavaScript

Attention all TypeScript and JavaScript programmers!

Have you ever heard of astral symbols?

Astral symbols, also known as astral plane characters, are a fascinating and important part of Unicode. They are characters that require more than one code unit to represent and are outside of the Basic Multilingual Plane (BMP) - the first 65,536 code points in Unicode. Examples of astral symbols include emoji, uncommon Chinese characters like "龘" (U+9F98), and musical symbols like "𝄞" (U+1D11E).

So, what's the problem with astral symbols when it comes to programming in TypeScript or JavaScript? The issue arises when working with methods that operate on strings at the code unit level, such as substring, split, and replace. Since astral symbols require more than one code unit to represent, these methods may produce unexpected behavior when processing strings that contain astral symbols.

Take `substring` for example. Let's say we have a string that contains emojis and text: "🦄🌈✨sometext". If we use substring to grab the first three characters of the string like this:

// Example: Using substring to extract a substring containing astral symbols
const str = "🦄🌈✨sometext";
const substr = str.substring(0, 3);
console.log(substr); // outputs "🦄�"

We end up with a question mark inside a square box, which represents an invalid character. This is because the `substring` method does not properly handle astral symbols, which are represented by two code units in UTF-16 encoding.

To avoid this issue, we can convert the string into an `array` of characters and, using the `split` method, take the first three elements of the array, and then join them back into a string using the `join` method.

// Example: Using an array and join to extract a substring containing an astral symbol
const str = "🦄🌈✨sometext";
const astralArr = Array.from(str);
const substr = astralArr.slice(0, 3).join('');
console.log(substr); // outputs "🦄🌈✨"

Other methods like `split` and `replace` can also lead to unexpected behavior when dealing with astral symbols. To ensure your code works correctly, be sure to test it thoroughly with strings that can contain these type of characters.

In summary, astral symbols are an important part of Unicode, but they can cause issues when working with methods that operate on strings at the code unit level in TypeScript or JavaScript. By being aware of astral symbols and using appropriate methods, we can ensure our code works correctly and avoid unexpected behavior.
